## 구역

| 구역 | 역할 | 평시 상태 |
|---|---|---|
| **GCP 조직** | 주 운영 환경. 평시 CI/CD, 사내 서비스, 행위 기반 탐지, 격리 런북 | 운영 중 |
| **사고 대응 지휘** | 알림 수신, 분석, 승인(Human-in-the-loop). **GCP 밖에서 수행** | 알림 채널만 상시 운영 |
| **AWS 백업 계정** | 데이터만 불변 보관 (Object Lock Compliance). 아무도 자주 드나들지 않는 금고 | 항상 존재 (저장 비용만 발생) |
| **AWS DNS 계정** | Route 53 호스팅 영역. 평시에는 GCP, 사고 시에는 AWS로 전환 | 항상 존재 (월 0.5달러 수준) |
| **AWS DR 계정** | 클린 빌드, 오케스트레이터, 복원으로 서비스 재가동 | 평시에는 없음. 사고 시 Terraform으로 생성 |

### AWS 계정을 3개로 나누는 이유

AWS Organizations로 묶는다. 계정을 추가하는 비용은 없다. 관리(management) 계정에는 워크로드를 두지 않고, SCP로 백업 계정에서 S3 삭제와 Object Lock 변경을 막는 데만 쓴다.

- **DNS를 DR 계정에 두지 않는 이유**: DR 계정은 평시에 존재하지 않는다. 사고 때는 관리자 권한으로 만들고 지우기를 반복하므로, 실수나 자격증명 노출이 DNS까지 번질 수 있다
- **DNS를 백업 계정에 두지 않는 이유**: DNS 운영을 위해 사람이 드나들면 금고의 공격 표면이 넓어진다
- **DNS 계정 권한**: 사고 대응 담당자가 레코드를 바꾸는 권한만 둔다. GCP 파이프라인에는 DNS 쓰기 권한을 주지 않는다

## 핵심 설계 원칙

1. **사고 시 GCP에서 나온 것은 데이터 말고는 아무것도 믿지 않는다**: 이미지, 시크릿, 서명 키, DNS, 로그 파이프라인이 모두 해당된다
2. **Pull 방식 백업**: AWS 백업 계정이 Workload Identity Federation으로 GCP Export 버킷을 읽기 전용으로 가져온다. GCP에는 AWS 자격증명이 없다
3. **데이터만 백업**: DB 덤프, 첨부파일, IaC 코드, 감사 로그 사본만 대상이다. 컨테이너 이미지는 백업하지도 사전 복제하지도 않는다
4. **무결성 해시**: 백업할 때 SHA-256 매니페스트를 기록하고 복원할 때 다시 비교한다
5. **클린 빌드 파이프라인**: AWS 안의 러너에서 마지막으로 검증된 커밋을 빌드한다. 의존성 lock, SBOM, Trivy, SAST를 거치고 AWS KMS 신규 키로 cosign 서명한다. ECR은 태그를 불변으로 두고, 배포 시 서명을 검증한다
6. **사람이 승인한다**: GCP '신뢰 불가' 선언, 격리, DR 발동, 복원 시점 확정은 관리자 승인을 거친다. 승인 이후의 단계는 오케스트레이터가 자동으로 실행하고 타임스탬프를 기록한다 (RTO 측정)
7. **시크릿은 새로 발급한다**: DB 비밀번호, API 키, JWT 서명 키를 모두 AWS Secrets Manager와 KMS에서 새로 만든다
8. **탐지가 무력화될 것에 대비한다**: 공격자는 조직 권한으로 로깅과 SCC를 끌 수 있다. 그래서 알림은 즉시 외부 채널로 보내고, 감사 로그 사본은 AWS에 불변으로 보관한다
9. **DNS는 별도 AWS 계정의 Route 53에 둔다**
   - 도메인 등록기관(registrar) 계정도 GCP 밖에 두고 MFA와 registrar lock을 건다. NS를 바꿀 수 있는 등록기관 계정이 DNS의 최상위 권한이기 때문이다
   - 헬스체크 기반 자동 장애 조치는 쓰지 않는다. 침해된 GCP도 '정상'으로 응답하므로, 관리자 승인을 거쳐 수동으로 전환한다
   - TTL은 평시에도 60초로 낮게 유지한다. 전환에 걸리는 시간이 RTO에 그대로 포함된다
   - Cloudflare는 "AWS도 동시에 침해된다"까지 가정할 때만 의미가 있으므로 채택하지 않는다
