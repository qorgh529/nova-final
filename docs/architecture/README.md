## 구역

| 구역 | 역할 | 평시 상태 |
|---|---|---|
| **GCP 조직** | 주 운영 환경. 평시 CI/CD, 사내 서비스, 행위 기반 탐지, 격리 런북 | 운영 중 |
| **사고 대응 지휘** | 알림 수신, 분석, 승인(Human-in-the-loop). **GCP 밖에서 수행** | 알림 채널만 상시 운영 |
| **AWS 백업 계정** | 데이터만 불변 보관 (Object Lock Compliance). 아무도 자주 드나들지 않는 금고 | 항상 존재 (저장 비용만 발생) |
| **AWS DNS 계정** | Route 53 호스팅 영역. 평시에는 GCP, 사고 시에는 AWS로 전환 | 항상 존재 (월 0.5달러 수준) |
| **AWS DR 계정** | 클린 빌드, 오케스트레이터, 복원으로 서비스 재가동 | 평시에는 비용 0원인 **복구 제어 영역**만 존재. 워크로드는 사고 시 Terraform으로 생성 |

### AWS 계정을 3개로 나누는 이유

AWS Organizations로 묶는다. 계정을 추가하는 비용은 없다. 관리(management) 계정에는 워크로드를 두지 않고, SCP로 백업 계정에서 S3 삭제와 Object Lock 변경을 막는 데만 쓴다.

- **DNS를 DR 계정에 두지 않는 이유**: DR 계정에는 평시에 워크로드가 없다. 사고 때는 관리자 권한으로 만들고 지우기를 반복하므로, 실수나 자격증명 노출이 DNS까지 번질 수 있다
- **DNS를 백업 계정에 두지 않는 이유**: DNS 운영을 위해 사람이 드나들면 금고의 공격 표면이 넓어진다
- **DNS 계정 권한**: 사고 대응 담당자가 레코드를 바꾸는 권한만 둔다. GCP 파이프라인에는 DNS 쓰기 권한을 주지 않는다

## 핵심 설계 원칙

1. **사고 시 GCP에서 나온 것은 데이터 말고는 아무것도 믿지 않는다**: 이미지, 시크릿, 서명 키, DNS, 로그 파이프라인이 모두 해당된다
2. **Pull 방식 백업**: AWS 백업 계정이 Workload Identity Federation으로 GCP Export 버킷을 읽기 전용으로 가져온다. GCP에는 AWS 자격증명이 없다
3. **데이터만 백업**: DB 덤프, 첨부파일, IaC 코드, 감사 로그 사본만 대상이다. 컨테이너 이미지는 백업하지도 사전 복제하지도 않는다
4. **무결성 해시**: 백업할 때 SHA-256 매니페스트를 기록하고 복원할 때 다시 비교한다
5. **클린 빌드 파이프라인**: AWS 안의 러너에서 마지막으로 검증된 커밋을 빌드한다. 의존성 lock, SBOM, Trivy, SAST를 거치고 AWS KMS 신규 키로 cosign 서명한다. ECR은 태그를 불변으로 두고, 배포 시 서명을 검증한다
6. **사람이 승인한다**: GCP '신뢰 불가' 선언, 격리, DR 발동, 복원 시점 확정은 관리자 승인을 거친다. 승인 이후의 단계는 오케스트레이터가 자동으로 실행하고 타임스탬프를 기록한다 (RTO 측정). DNS 전환 직전에는 다시 승인을 기다린다
7. **시크릿은 새로 발급한다**: DB 비밀번호, API 키, JWT 서명 키를 모두 AWS Secrets Manager와 KMS에서 새로 만든다
8. **탐지가 무력화될 것에 대비한다**: 공격자는 조직 권한으로 로깅과 SCC를 끌 수 있다. 그래서 알림은 즉시 외부 채널로 보내고, 감사 로그 사본은 AWS에 불변으로 보관한다
9. **DNS는 별도 AWS 계정의 Route 53에 둔다**
   - 도메인 등록기관(registrar) 계정도 GCP 밖에 두고 MFA와 registrar lock을 건다. NS를 바꿀 수 있는 등록기관 계정이 DNS의 최상위 권한이기 때문이다
   - 헬스체크 기반 자동 장애 조치는 쓰지 않는다. 침해된 GCP도 '정상'으로 응답하므로, 관리자 승인을 거쳐 수동으로 전환한다
   - TTL은 평시에도 60초로 낮게 유지한다. 전환에 걸리는 시간이 RTO에 그대로 포함된다
   - Cloudflare는 "AWS도 동시에 침해된다"까지 가정할 때만 의미가 있으므로 채택하지 않는다

## 컴퓨팅 플랫폼: GKE + EKS (확정)

| 위치 | 선택 | 구성 |
|---|---|---|
| GCP 운영 | **GKE Standard** | 존 1개 클러스터, e2-medium Spot 노드 1~2대, Falco DaemonSet |
| AWS DR | **EKS** | 사고 시에만 Terraform으로 생성. GKE와 같은 매니페스트와 Helm 차트를 사용 |

**Cloud Run을 쓰지 않는 이유**
- Falco를 설치할 수 없다. 노드에 접근할 수 없는 샌드박스라서 ③단계의 런타임 탐지가 불가능하다
- 노드 디스크가 없어 ④단계의 포렌식 스냅샷을 뜰 수 없다
- 공격 표면이 작아서 침해 데모(파드 → 메타데이터 서버 → 토큰 탈취)를 보여주기 어렵다

**GKE Autopilot을 쓰지 않는 이유**
- 노드 접근이 제한되어 Falco 설치가 불확실하다. Standard를 쓰면 이 문제를 피할 수 있다

**EKS를 쓰는 이유 (ECS 대신)**
- GKE와 같은 Kubernetes 매니페스트를 그대로 쓸 수 있다. 복구할 때 재작성이 필요 없어 RTO가 줄어든다
- Falco와 cosign 서명 검증(admission policy)을 양쪽에 같은 방식으로 적용할 수 있다
- 발표에서 "도구는 같고 **신원 체계만 다르다**"는 메시지가 분명해진다

**비용**
- GKE: 클러스터 관리비는 무료 크레딧으로 상쇄된다. 노드 비용만 든다
- EKS: 컨트롤 플레인 요금이 시간당 0.1달러다. DR 계정은 사고나 데모 때만 존재하므로 몇 시간 분량만 든다
- 실제 금액은 확정 전에 요금 계산기로 확인한다

## CI/CD: Cloud Build + CodeBuild, PR 테스트는 GitHub Actions (확정)

| 용도 | 도구 | 가진 권한 |
|---|---|---|
| PR 테스트 (단위 테스트, 린트, SAST) | **GitHub Actions** | **클라우드 자격증명 없음** |
| 평시 빌드와 GCP 배포 | **Cloud Build** (GitHub App 트리거) | GCP 서비스 계정만. 시나리오에서 **오염되는 쪽** |
| 사고 시 클린 빌드 | **AWS CodeBuild** (DR 계정, Terraform으로 생성) | AWS KMS 신규 서명 키, ECR 푸시. GitHub는 읽기 전용 연결 |

**평시 빌드를 Cloud Build로 하는 이유**
- 빌드가 GCP **침해 범위 안**에 있다. GCP를 신뢰할 수 없게 되면 평시 파이프라인도 쓸 수 없으므로, AWS에 클린 파이프라인이 필요하다는 논리가 자연스럽다
- 평시 파이프라인을 GitHub Actions로 하면 "그냥 GitHub Actions로 AWS에 빌드하면 되지 않나?"라는 질문이 생긴다. 게다가 클린 빌드도 같은 플랫폼(워크플로, 시크릿, 서드파티 Action)을 공유하게 되어 분리가 약해진다
- 빌드 provenance와 Binary Authorization attestation을 바로 만들 수 있다. "탈취된 파이프라인이 서명했기 때문에 Binary Auth를 통과했다"를 시연하기 쉽다

**GitHub에는 어떤 클라우드 자격증명도 두지 않는다**
- GitHub는 소스만 제공한다. 클린 빌드는 승인 단계에서 확정한 **커밋 SHA를 고정**해서 가져오므로, 소스 신뢰를 커밋 단위로 보장한다
- 근거 사례: 2025년 3월 `tj-actions/changed-files` 침해로 여러 저장소의 워크플로 시크릿이 로그로 노출됐다 (발표 전 원문 확인 필요)

**공격 흐름 (Cloud Build 기준)**
1. 빌드 중 오염된 의존성이 실행되고, 메타데이터 서버에서 Cloud Build 서비스 계정의 **토큰**을 얻는다 (서비스 계정 키 파일은 따로 없다)
2. 이 토큰으로 **새 SA 키, 숨은 서비스 계정, IAM 바인딩**을 만들어 지속성을 확보한다. Audit Logs와 SCC가 이를 탐지한다
3. 배포된 이미지는 런타임에 모의 C2로 신호를 보낸다. Falco와 VPC Flow Logs가 이를 탐지한다

## 백업 Pull 작업: Lambda (확정)

**흐름**
1. GCP: Cloud Scheduler가 Cloud SQL을 GCS로 내보내기한다 (DB 덤프). 첨부파일 사본, 감사 로그 사본, 결재 이력 체인 헤드 해시와 함께 Export 버킷에 매니페스트(파일 목록과 SHA-256)를 쓴다
2. AWS 백업 계정: EventBridge Scheduler가 Lambda(Python)를 실행한다
3. Lambda가 실행 역할의 AWS 자격증명을 Workload Identity Federation으로 GCP 토큰과 교환한다. Export 버킷 읽기 전용 권한만 받는다
4. GCS에서 읽은 데이터를 S3 멀티파트 업로드로 **스트리밍 복사**하면서 SHA-256을 계산한다. 첨부파일은 지난 실행 이후 새로 생긴 객체만 **증분 복사**한다. GitHub의 IaC 코드도 같은 방식으로 가져온다
5. **이중 확인**: GCP 매니페스트의 해시와 Lambda가 직접 계산한 해시를 비교한다. 업로드할 때는 S3 체크섬(SHA-256)을 지정해서 S3도 저장 시점에 검증하게 한다. 하나라도 다르면 실패로 처리하고 외부 채널로 알린다
6. AWS 쪽 매니페스트(파일 목록, 해시, 체인 헤드 해시, 실행 시각)를 Object Lock 버킷에 기록한다. 이 매니페스트가 복원 시 무결성 검증의 기준이 된다
7. 백업 크기, 소요 시간, 성공 여부를 CloudWatch 지표로 남긴다 (RPO 근거)

**Lambda를 고른 이유 (ECS Fargate Task 대신)**
- 금고 계정의 공격 표면이 작다. 함수, 역할, 스케줄만 있으면 되고 VPC, NAT, ECR 이미지가 필요 없다. 이미지가 없으니 "금고에 이미지를 누가 푸시하나"라는 공급망 문제도 생기지 않는다
- 평시 비용이 사실상 0원이다. Fargate를 프라이빗 서브넷에서 쓰면 NAT Gateway 비용(월 30달러 이상)이 들어서 "평시 비용은 월 몇 달러"라는 논리가 깨진다
- DB 덤프는 GCP 쪽에서 만들고 AWS는 복사만 한다. AWS가 Cloud SQL에 직접 접속할 필요가 없으므로, 두 클라우드 사이 연결이 Export 버킷 읽기 하나로 끝난다
- 데모 규모의 데이터는 15분, `/tmp` 10GB 제한 안에 충분히 들어온다

**ECS Task로 바꾸는 기준**
- 파일 하나가 15분 안에 복사되지 않을 만큼 커질 때
- 덤프를 실제로 복원해 보는 복원 테스트가 필요할 때. 이 작업은 금고가 아니라 DR 계정에서 한다

## 복구 오케스트레이터: 스크립트 + Step Functions 혼합 (확정)

실제 작업은 **CodeBuild 안에서 도는 Make 타깃과 셸 스크립트**가 한다. Step Functions는 그 위에서 순서, 병렬 실행, 승인 대기, 시각 기록만 맡는다.
Terraform apply, 클린 빌드, `pg_restore`는 Step Functions가 직접 할 수 없으므로, 어느 방식이든 실체는 스크립트다.

### 흐름

```
[관리자 승인: DR 발동, 복원 시점 T0 확정]
        │
        ▼
 ┌─ 병렬 ───────────────────────────────┐
 │ ① 인프라: make infra                  │   ② 클린 빌드: make build
 │   (VPC, EKS, RDS, S3, Secrets, KMS)  │      고정 커밋 SHA → SBOM, Trivy → cosign → ECR
 └──────────────────────────────────────┘
        ▼
 ③ 데이터 복원: make restore T0=...
    T0 이전 백업 선택 → 매니페스트 해시 검증 → 첨부파일 ClamAV 스캔
    → pg_restore → 권한 테이블 점검 → 해시 체인 검증
        ▼
 ④ 배포: make deploy (Helm, 이미지 digest 고정, 배포 시 서명 검증)
        ▼
 ⑤ 스모크 테스트: make smoke (/actuator/health, /version digest, /api/admin/integrity)
        ▼
 ⑥ [승인 대기] DNS 전환: DNS 계정 담당자가 전환 스크립트 실행 → Step Functions에 완료 신호
        ▼
 ⑦ 사후 검증: make verify (GuardDuty, Flow Logs 확인, RPO 계산) → RTO/RPO 보고서 생성
```

### 원칙

- **각 단계는 다시 실행해도 결과가 같아야 한다**: 실패하면 그 단계부터 다시 실행한다
- **스크립트는 Step Functions 없이도 돌아야 한다**: 로컬이나 CodeBuild 단독 실행으로 테스트하고 리허설한다
- **DNS 전환은 오케스트레이터가 직접 하지 않는다**: DNS 계정 권한은 사고 대응 담당자에게만 있다. 담당자가 전환 스크립트를 실행하면, 그 스크립트가 Step Functions 콜백(task token)으로 완료를 알린다
- **시각 기록**: Step Functions 실행 이력에 상태별 시작·종료 시각이 자동으로 남는다. ⑦단계에서 이를 모아 RTO/RPO 보고서(JSON, Markdown)를 만들어 S3에 저장한다
- **운영자 노트북에서 복구를 실행하지 않는다**: 노트북 자체를 믿을 수 있는지가 문제가 되고, 실행 기록을 재현할 수 없다

### 복구 제어 영역은 평시에 미리 둔다

| 구성 요소 | 평시 비용 |
|---|---|
| Step Functions 상태 머신 | 0원 (실행할 때만 과금) |
| CodeBuild 프로젝트 (인프라, 클린 빌드, 복원, 배포, 검증) | 0원 (빌드 시간만 과금) |
| Terraform 상태 버킷 (S3), 잠금 테이블 (DynamoDB 온디맨드) | 거의 0원 |
| IAM 역할 (GCP 자격증명 없음) | 0원 |

- 사고가 나면 실행만 하면 되므로 **RTO가 줄어든다**
- 평시에 **복구 리허설**을 해서 RTO를 미리 측정할 수 있다. 리허설이 끝나면 워크로드만 `terraform destroy`로 지운다
- 제어 영역에는 GCP 자격증명이 전혀 없어서 공격 표면이 사실상 늘지 않는다

### 단계적 구현

1. **1단계 (MVP)**: Make 타깃을 CodeBuild 하나에서 순서대로 실행한다. 단계별 시각은 JSON으로 S3에 기록한다
2. **2단계 (발표 전)**: 같은 스크립트를 Step Functions로 감싸서 병렬 실행, 승인 대기, 진행 그래프를 추가한다
